# Enhanced CDC and reset stress testbenches

This folder contains standalone stress versions of the canonical benchmark
testbenches. The validated baseline TBs remain under `benchmarks/*/tb/`.

All added monitors use procedural Verilog (`always`, registers, counters,
arrays, tasks and `$display`). They do not use SVA, `property`, `bind`,
`$past`, classes, or queues.

## Intended checks

- independent and mid-transaction reset assertion
- reset-release recovery and bounded progress
- source/destination transaction conservation and ordering
- no duplicated, lost, stale, or unknown payloads
- valid/data/sideband stability while stalled
- pulse exactly-once and one-destination-cycle width
- FIFO overflow, underflow, occupancy and clear behavior
- request/response accounting for APB, AXI, AXI-Stream and Wishbone
- clock-ratio and phase stress where the DUT has multiple clocks

Not every check applies to every circuit. Single-clock circuits receive
reset, unknown-value, liveness and protocol checks, but are not described as
CDC designs.

## Structural limitation

RTL simulation cannot model metastability or prove synchronizer depth,
foreign asynchronous reset usage, Gray-pointer correctness, or missing
two-flop chains. Continue running the repository-owned
`cdc_tb_checks/lint_cdc.py` before these testbenches. Proprietary formal tools
may be reported as optional secondary evidence, but they are not part of the
strict-pass definition.

## Typed evidence

Each detected error emits a stable rule ID as either
`CDC/RESET VIOLATION [RULE_ID]` or `PROTOCOL VIOLATION [RULE_ID]`.
The former is eligible for automatic CDC/reset confirmation; the latter is
kept as functional/protocol evidence. Untyped summaries remain ambiguous.
See [RULES.md](RULES.md) for the classification contract.

Audit all 44 enhanced testbenches after editing messages or checks:

```bash
python3 enhanced_cdc_tb/check_typed_evidence.py
```

## Layout

- `fifo/`: asynchronous FIFOs and FIFO-based stream crossings
- `bus/`: APB, AXI, AXI-Stream, Wishbone and peripheral protocols
- `sync/`: synchronizers, pulses, reset generators and reset controllers
- `handshake/`: 2-phase/4-phase and isochronous handshakes
- `results/`: generated by the enhanced runner
